## Recommendation

Fix refresh coordination first. Keep ordinary authenticated request/response APIs and explicit mutations. For this purchase-records application, continuous bidirectional communication is not currently required. The frontend needs notification that an import/status projection changed; backend work already runs independently in queues. Polling is a reasonable bounded fallback, but the present implementation has avoidable request amplification and foreground-event duplication.

If measured product requirements demand immediate import updates after those fixes, implement small server-to-client invalidations, with authenticated snapshot fetches remaining authoritative. SSE fits that one-way contract; hibernating WebSockets with a per-tenant Durable Object fit Cloudflare's coordinated fanout particularly well if connection cost/scale justifies a new binding. Neither is a drop-in transport substitution: publishers across queue, scheduled and mutation invocations need a shared rendezvous. Do not create a DO or deploy a new realtime service solely to eliminate one timer.

Do not implement long polling by repeatedly executing the full onboarding projection inside a held request. It can reduce visible browser request count while increasing D1 reads and retaining long-lived invocations. Without a shared notification mechanism it merely moves polling into the backend.

## Findings and smallest fixes

1. **P2: hidden and paused onboarding work still polls.** At `apps/web/src/onboarding/page.tsx:153-157`, only missing progress/historyComplete stop polling. Visibility and `paused_budget`, `needs_reconnect`, `processing_unavailable` are not gates. Reproduction: show an incomplete paused import, then hide the tab; scheduled refresh remains registered (browsers may throttle it). Consequence: repeated authenticated projection reads with no actionable progress and mobile wakeups. Fix: poll only actionable running work while visible; stop or substantially slow paused states, preserving manual and foreground refresh for external recovery. Test hidden/visible, paused/running, completion and error backoff.

2. **P2: foreground events lack coordination.** Onboarding `:123-135`, private `:473-489`, recurring `:107-123` independently handle focus/pageshow/visibility. One tab restoration can produce multiple events. Onboarding aborts the previous controller (`:52`) rather than coalescing requests; private/recurring revision changes restart their effect. Browser abort does not prove already-arrived server work was canceled. Fix: coalesce a foreground event burst and in-flight refreshes, while prioritizing actual actor/mailbox changes over dedupe. Require one logical refresh for a restoration burst, no stale-result commit, immediate post-mutation invalidation, and account-change clearing. A debounce must not leave previous-actor data visibly exposed while authorization is pending.

3. **P3: blanket private reloads can disrupt a form.** Private/recurring foreground handlers replace ready state with loading before reloading (`private/page.tsx:475`; `recurring/page.tsx:109`). Unmounting descendants can discard local drafts. Fix in a separate tightly scoped change: define when background freshness may retain a verified same-actor view and how stale/failed auth clears it; add an unsaved-draft restoration test. Do not retain stale private data without identity checks merely for visual smoothness.

4. **Not a finding: processing-disclosure callback churn.** Onboarding `load` depends only on `selected` (`:107`), `identityChanged` is memoized (`:109-115`), and `refresh` is memoized (`:116-118`). Review `loadReview` depends on actor, connection, stable identity callback and scalar profile settings/email (`review.tsx:143-151`). A new `workspace` object with unchanged scalars does **not** reload disclosure. Inline `onStarted`/`onChooseMailbox` at page `:388-395` are not loadReview dependencies. The advanced-settings effect also uses actor/stable identity callback. No automatic 15-second disclosure reload is inferred from these files. A real settings or selected-mailbox change correctly invalidates the consent projection.

## Transport comparison

| Option | Latency and database work | Lifecycle and operational effects |
| --- | --- | --- |
| Coordinated, visibility-aware polling | Active updates appear within poll interval plus request time; fewer wasted reloads. Still repeats auth/projection reads while running. | Lowest implementation cost. Each request revalidates session. One in-flight request, bounded backoff/jitter, hidden-tab stop and resume snapshot are enough. Measure refresh cause, request count, duration and safe failure class. |
| Bounded long poll (proposed 25 seconds) | With event notification: wakes immediately on change and otherwise returns timeout. With a D1 loop: database polling frequency determines latency; full projection checks can cost more than current client polling. A 25-second timeout is a proposed application bound, not a Cloudflare platform maximum. | One outstanding wait/tab; cap waits/tenant; cancel on hide/unmount and jitter retries. Authenticate each wait and before returning sensitive data; revocation must also close or deny an already-open wait. Track open waits, timeouts, cancellation, wakes and DB work. Shared wakeup owner still required for queue events. |
| SSE invalidations | Immediate one-way event, followed by existing snapshot fetch; D1 queries become change/reconnect dependent only if publishers emit events. Streaming a D1 polling loop provides no such saving. | HTTP stream and event ids are a natural fit for status updates. Cap connection lifetime/tenant and coalesce notifications; close on hidden tab, revalidate on resume, handle reconnect with backoff and snapshot repair. SSE lacks the documented DO WebSocket hibernation benefit. Monitor active streams, lag, reconnects, dropped/coalesced notifications and auth closures. |
| Hibernating WebSocket + tenant DO | Immediate invalidations; low steady D1 read volume if queue/mutation publishers emit post-commit events rather than polling. Snapshot reads still happen on reconnect/change. | New DO class/binding/migration, publishers and lifecycle tests. Server-owned tenant selection; cookie-authenticated, origin-checked upgrade. Serialize only safe connection metadata for hibernation. Explicit revocation/session-expiry/account-delete closure or bounded reauthorization. Bounded outbound work; coalesce slow-consumer events and reconnect to a snapshot. Heartbeat timers can defeat hibernation. Track active sockets, notification lag, publish failures, rejected upgrades, auth closures, reconnect rate and duration/cost. |

All transports need mobile/offline/sleep/deployment reconnect behavior. Best-effort invalidation plus authoritative snapshot repair is sufficient for this UI; do not introduce durable event replay or send purchase documents/values over a new channel. A disconnected browser must never block queue progress. A notifier failure after a committed business write must not cause duplicate external processing or falsely roll back the successful write; periodic/foreground reconciliation is the recovery path. Do not adopt a second business database in the DO.

## Verified platform constraints and documentation gaps

Context7 tool resolution/query capabilities were not exposed in this session (searched enabled tool metadata). Fell back to current official Cloudflare docs, retrieved 2026-10-13. No third-party tutorial used.

- Workers support WebSocket endpoints; coordinated connections use Durable Objects. [Workers WebSockets](https://developers.cloudflare.com/workers/runtime-apis/websockets/)
- DO hibernation retains the client connection while resetting in-memory state and avoiding idle billable duration; serialized connection attachments restore metadata. Timers/events can prevent hibernation. Requires a DO binding and migration. [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- HTTP service bindings forward Request objects using `fetch`. Pages also documents service bindings. The current proxy already returns `env.API.fetch(new Request(...))` directly (`apps/web/functions/api/[[path]].ts:1-15`), stripping untrusted identity/forwarded headers. [HTTP service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/http/), [Pages bindings](https://developers.cloudflare.com/pages/functions/bindings/)
- HTTP-triggered Workers have no hard wall-clock duration limit while the client remains connected; disconnect can cancel associated work. This permits streaming/bounded waits but does not establish their load/cost fitness. [Worker limits](https://developers.cloudflare.com/workers/platform/limits/)
- Cloudflare documents EventSource and a fetcher extension for bindings. This proves runtime SSE support; it does not prove the application's complete browser-to-Pages-to-Worker cancellation path. [EventSource](https://developers.cloudflare.com/workers/runtime-apis/eventsource/)

The HTTP service-binding reference inspected did not explicitly describe WebSocket upgrades. Treat end-to-end preservation of 101/webSocket through this particular Pages route, connection cancellation, close behavior and staged deploys as an integration/staging evidence gate, not a verified deployed fact. No websocket/upgrade/SSE/DO production implementation or binding was found in `apps`/`packages`; checked-in Worker config currently has only D1, with job/extraction enablement off.
