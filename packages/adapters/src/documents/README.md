# T10 transient document parsing

`normalizeGmailDocumentInput` normalizes a **supplied** Gmail full payload and attachment map into the provider-neutral `DocumentInput`. It does not fetch mail or attachments; T09 remains metadata-only. The authorized later processing job supplies content and a trusted tenant context. Connection/message/part identifiers are exact provenance, including Gmail's empty root part ID, and are never user authorization or outbound destinations.

The core `createDocumentTextExtractor({ pdf?, limits? })` validates the whole recursive MIME tree before extraction. Defaults and hard maxima are 4 MiB aggregate decoded bytes, 64 nodes, depth 8, 20 aggregate PDF pages, and 24,000 aggregate text characters. Gmail headers are separately bounded to 8,192 characters. Declared attachment lengths, canonical padded/unpadded base64url and pad bits are validated. Duplicate part identifiers and missing attachment content fail closed. Raw RFC MIME parsing and content-transfer decoding are outside this adapter: Gmail supplies decoded part bytes through its base64url response representation.

Multipart alternatives select one body, preferring nonempty plain text. Mixed MIME retains each genuine attachment with exact part identity and SHA-256 of original decoded bytes. Inline images with inline/content-ID evidence are ignored; image attachments receive explicit review without invented OCR. No cross-part invoice merging or financial acceptance happens here.

HTML becomes inert plain text. The tokenizer never constructs a DOM, follows links, executes scripts, or fetches CSS/images. It strips scripts/styles, nested hidden/active containers and forms, checks exact closing-tag boundaries, and preserves visible numeric labels and values. Known PDF/image/archive/executable signatures labelled as text fail MIME consistency checks before decoding. Malformed/truncated output and aggregate overflow return incomplete/review without partial receipt text.

`createLocalPdfTextExtractor()` uses pinned **unpdf 1.8.1** and its bundled serverless PDF.js build. Its verified support is a narrow **uncompressed text-layer PDF subset**, not general PDF or OCR. A bounded conservative lexical guard rejects compressed/filter/object-stream/encrypted/action/embedded-font features and excessive nesting/token volume before PDF.js. It can reject harmless PDFs that mention these feature names; those require review rather than a guessed conversion. The library handles actual parsing; there is no custom PDF parser, decompressor, Node daemon, native canvas, rendering path, or hosted fallback.

The adapter uses original bytes only, disables external worker fetch/auto-fetch/Wasm/image decoding/font face/XFA, sets silent parser logging, checks page count, and streams text sequentially with an output bound. Every page must contain text; a scanned/mixed textless page is review. Reader cancellation and document destruction run after success/failure. The generated two-page binary fixture verifies exact subtotal/tax/total/card-paid evidence on the final page. A real generated image-only PDF remains review; a genuinely deflated 1 MiB stream is rejected while its compressed PDF is under 8 KiB.

All bytes, normalized text and evidence quotes are transient. The modules expose no database, queue, log, or original-storage port. Only identities, hashes and bounded parser status/version metadata are suitable for later persistence. No hosted processor, image/OCR capability, resource, provider request or model charge is enabled. External parsing requires a separate environment-selected approved adapter, explicit policy/consent and budget integration; absence never silently selects another destination.

T10 preserves numeric evidence; T11/T12 choose and validate actual paid/refund amounts. The synthetic tests are parser/runtime evidence, not extraction-model accuracy or production memory/CPU/Free-plan viability measurements.
