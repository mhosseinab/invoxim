# Durable jobs (T07)

`createJobStore(db, { policy, clock?, id? })` provides the D1 job port. Construct a **fresh store per Worker invocation**: its private execution counter covers every actual `first`, `all`, `run`, `raw`, and batch statement in this module. Production configuration permits 24–40 statements, defaults to 40, and leaves headroom below D1's documented 50-query Free invocation limit. This is a query bound, not evidence of CPU, cost, or deployed-plan viability. Other application/provider persistence must share the invocation's remaining capacity when those integrations are added.

At 40, recovery receives at most 8 statements, hourly scheduling 8, candidate selection 14, leaving 10 reservation statements. At 24 the corresponding ceilings are 8/8/4/4. Smaller synthetic test budgets exercise fail-closed exhaustion; 16 allows dispatch progress and expired-lease recovery but does not run the full invalid-ready cleanup sweep. Budget exhaustion executes no further statement, exposes only `JOB_QUERY_BUDGET`, and causes transport retries or defers the outbox to a later sweep.

Recovery first fetches one expired lease through the global lease index, then conditionally retries, cancels, or terminates it with a fence check. It also inspects at most two identifiers in one tenant's persisted recovery cursor and cancels invalid pending work. This skips no unchanged valid prefix forever. The tenant cursor advances only after processing, with its write reserved in the stage ceiling. An empty page resets the cursor for the next invocation.

Hourly scheduling considers one tenant and one eligible due connection per sweep. A pending incremental job excludes that connection from periodic selection; manual sync coalesces an existing pending ID and enforces a five-minute cooldown. A conditional D1 batch rechecks active profile, connection generation, schedule activation, exact consent, and absence of another pending incremental job before inserting the live sync state/job or changing scheduling metadata. `awaiting_import` never creates content work.

Candidate selection visits at most five tenants, takes at most two candidates per tenant, and alternates tenant slots. Each of three indexed priority branches reads at most two identifiers before authorization checks, so one candidate query inspects at most six identifiers. Actual work can be smaller than the configured dispatch maximum; a sweep is not promised to send 50 messages. Continuous valid backlog in an earlier tenant does not prevent the processed-tenant cursor from reaching later tenants.

Dispatch reserves a candidate with its original fence and dispatch timestamps **before** sending the opaque `{ schemaVersion: 1, jobId }` envelope. A failed/lost send becomes eligible after the redelivery deadline. Claims acquire a lease and increment its fence/attempt atomically while enforcing tenant and global active-lease quotas. Checkpoint and completion require current generation/consent/profile and an unexpired matching lease. Retries have bounded backoff/attempts; terminal status plus a bounded outcome code is the durable diagnostic.

The core engine recognizes already-completed financial commits before ACK, including retries after a crash following the atomic source commit. Missing handlers pause with `handler-unavailable`; a lost pause fence retries instead of ACK. Handler/admission operations are bounded by the lease deadline and receive an abort signal/checkpoint. The runtime explicitly ACKs or retries native queue messages, uses two consumers, and retries messages beyond its 50-envelope bound.

This module does not implement ingestion, provider calls, inference budgets, settings revision policy, reconnect APIs, a scheduler UI, deployments, or resources. Admission and handlers are configured application ports; no handler means no fabricated processing result. Consent destination revision checks will be integrated with the later AI-settings contract. Indexes/migration upgrade and concurrency tests use only synthetic local D1 data.
