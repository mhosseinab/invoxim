## Contract and identity

`createOutlookAuthorization({clientId, clientSecret, authority?})` implements the unchanged core MailboxAuthorizationPort. Configuration uses only validated server environment/Wrangler bindings: OUTLOOK_ENABLED exact `true`, OUTLOOK_CLIENT_ID, OUTLOOK_CLIENT_SECRET, OUTLOOK_AUTHORITY, CREDENTIAL_KEYRING, MAILBOX_LIMIT and the existing validated login/DB bindings. Default disabled. Authority is common, consumers, organizations or one case-normalized tenant GUID; arbitrary URLs, host overrides, sovereign clouds and query/path injection are rejected. Callback is fixed `/api/oauth/mailbox/outlook/callback`. Google app login remains independent from Microsoft mailbox consent.

Scopes are exactly openid, profile, email, offline_access and https://graph.microsoft.com/Mail.Read. No Mail.ReadBasic, Mail.ReadWrite, User.Read, application scopes, `.default` or account-wide admin operation. The existing Microsoft authorizer builds code/S256 PKCE/state; an independently bound nonce is attached. Shared state/session one-use guards remain root-owned. Token/refresh requests include only the fixed chosen authority, application credentials and exact requested scopes. Token responses require delegated Mail.Read and reject unexpected broader granted scopes when a scope response is present. Initial missing scope fails closed; refresh missing scope inherits the established grant and still proves the access identity.

Initial identity is a cryptographically verified issuer plus immutable pairwise subject: `${iss}|${sub}`, bounded below the common 254-character subject limit. Address is display metadata only; initial UserInfo email must be a valid address, otherwise controlled MISSING_PERMISSION. There is no fallback to Google login email, mutable username or an invented mailbox address. Graph UserInfo sub must match the signed token's sub before credentials/read capability are returned.

Initial verification reuses pinned BetterAuth 1.7.7's publicly exported `verifyProviderIdToken` and Microsoft issuer/account-class verifier. Its default unbounded JWKS getter is overridden with bounded JSON from a fixed Microsoft keys URL, a validated selected RSA public JWK imported by native WebCrypto, and per-verification selected-key issuer checks against verified claims. JWT parsing/signature/audience/nonce/expiry/age remain the library's responsibility, with RS256 explicitly pinned. Claims require canonical GUID tenant, exact v2 issuer binding, immutable bounded subject, positive iat/exp and version 2.0. Common accepts work/personal; consumers, organizations and fixed GUID enforce their class/tenant restrictions. Selected key issuer may be the documented tenant template or the exact verified issuer. Unknown/duplicate key IDs, wrong signature/key issuer/audience/nonce/token version and expired/future tokens fail. Verification state is request-local, including simultaneous work/personal exchanges.

Refresh always validates the stored fixed-host issuer/tenant/account-class and proves the new opaque access token through fixed Graph UserInfo. Its pairwise sub must equal the stored sub. Microsoft documents sub as based on token recipient, tenant and user; it cannot be reused across accounts. This safely supports refresh responses with no ID token. Optional/unsigned refresh ID token claims are ignored completely and never choose authority, identity or destination. Rotated refresh tokens are returned for the shared encrypted store, and omitted replacement tokens retain the current token. Invalid grant maps to redacted RECONNECT_REQUIRED. No retry or provider fallback occurs in this adapter.

All provider JSON responses use manual redirects, a 10-second AbortSignal and streamed 65,536-byte cap. Content-length is checked before consumption and stream size is independently checked. Body reads also race the abort signal. Unknown/malformed JSON and network/redirect/size failure produce controlled errors; raw provider descriptions/tokens are not logged or returned as error detail. Fetch destinations never derive from token claims, metadata endpoints or UserInfo fields. Authorization performs no database writes, content fetch, discovery, queueing, model call or login-account merge.

## Current documentation verification

Context7 tools were unavailable in this session. Used primary Microsoft documentation and the actual pinned BetterAuth public exports/types/source, not transitive imports or a handwritten JWT verifier:

- [Microsoft OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc): account-class authority and fixed public-cloud endpoint semantics.
- [ID-token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference): immutable pairwise sub derives from recipient, tenant and user; email/username are mutable display values.
- [Microsoft UserInfo](https://learn.microsoft.com/en-us/entra/identity-platform/userinfo): openid/profile/email suffice for personal and work accounts, UserInfo sub equals the ID-token value, Graph access tokens are opaque. The repository pins this documented public endpoint instead of following untrusted metadata URLs.
- [Authorization-code/refresh flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow): code/PKCE/offline refresh; refresh ID token may be optional/unsigned, so no refreshed ID-token authority is assumed.
- Pinned BetterAuth 1.7.7 `better-auth/oauth2` reexports `verifyProviderIdToken`; `better-auth/social-providers` exposes Microsoft's typed `idToken` verification config. Source inspected under installed @better-auth/core 1.7.7 `social-providers/microsoft-entra-id.mjs`, `oauth2/verify-id-token.mjs`, `oauth2/create-authorization-url.mjs`. No new jose declaration or undeclared transitive import was needed.
