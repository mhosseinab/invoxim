# Login authentication boundary (T05)

`createLoginAuth(DB, configuration)` uses Better Auth 1.7.7 with its verified Drizzle/D1 schema. The restored mapping keeps INTEGER epoch-millisecond auth timestamps and Boolean storage; Worker composition shares a native query meter across auth and repositories. The HTTP composition creates a fresh auth instance for **each request**; never cache or share an instance across callback requests. The `handleLoginCallback` entry point is one-shot per instance, with request-local new-user tracking. The wrapped database adapter records newly inserted user IDs before queued library hooks, only while this callback is active. Its cleanup deletes only users newly created by that callback with neither an account nor a session, allowing a fresh-state retry after a failed account write. It never sweeps existing users or merges by email. Database outage during cleanup can still require operator reconciliation; it cannot authorize session access or recreate a deleting profile.

The default is disabled. `AUTH_ENABLED` must be exactly `true` and DB, a fixed HTTPS `AUTH_ORIGIN`, secret (at least 32 characters), Google client ID/secret, and a nonempty JSON array of exact `AUTH_ALLOWED_EMAILS` must validate. Real deployment/client configuration and independent review are operator prerequisites. Public-config and UI remain disabled until separately enabled by the operator. Never put secrets in public Vite variables.

Google login requests only `openid email profile`, uses online access, disables incremental granted scopes and client ID-token sign-in, and prompts account selection. Better Auth owns PKCE, signed browser state correlation, ten-minute state expiry/one-use consumption, provider callback routing and session cookies. A fixed provider extension sets its nonce flag, forwards the library-generated nonce, and calls the library's public `verifyGoogleIdToken` helper against Google's fixed certificates endpoint before its normal profile mapping. It verifies RS256 signature, Google issuer, configured audience, token age, explicit future expiry and expected nonce; subject, verified email and bounded profile fields are required. Exact allowed email is checked for new and returning OAuth identities. All account linking is disabled.

No login provider access/refresh/ID token is retained. Account create/update hooks discard token material and scope/expiry fields before the database adapter writes it; account cookies are disabled. Session cookie caching is disabled so logout/expiry/deleting status are checked against D1. Session cookies are Secure, HttpOnly, SameSite=Lax, path `/` and host-scoped (no Domain). Request headers and body/query user IDs never establish authority. The sole internal TenantContext assertion occurs after signed-session verification and active-profile lookup.

The Worker adapter provides fixed sign-in, Google callback, sign-out and a safe get-session projection under `/api/auth`, plus `GET/PATCH /api/me`. Mutation origins must exactly match the configured origin; JSON bodies are strict and limited to 4096 bytes. Caller-selected scopes, ID tokens, arbitrary callback URLs and provider parameters are rejected. Unknown library routes are not exposed. Provider descriptions are removed from callback redirects and failures use a generic error code. Auth/profile responses are no-store and expose no bearer token or provider credential. Unexpected database/provider errors are mapped to generic unavailable responses without raw details; the library logger is disabled.

Profiles are created on identity provisioning without mailbox connections, consent, import jobs, Drive or model calls. PATCH preferences uses an active-tenant predicate and expected version. Originals are not converted by a preference change; valuation rebuilding is a later T19 capability, and the projection explicitly reports `valuation.status = not_configured`. Account deletion and mailbox authorization remain later task boundaries.

Synthetic workerd tests use real D1/session/callback/library/WebCrypto paths with exact Google transport interception and generated RSA/JWK fixtures. These prove application behavior locally; they are not live Google or deployed OAuth evidence. AUTH-02's complete login-A/mailbox-B journey depends on the separate mailbox adapter in T08. No live provider request, deployment, credential or paid service is part of T05 verification.
