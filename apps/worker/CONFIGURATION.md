# Server configuration seams

External adapters are constructed from validated environment bindings at the Worker boundary. Keep provider SDKs and environment reads out of core. The server JSON preset selects Abacus RouteLLM GPT-6 Luna with the approved application budget. Platform secrets provide credentials; validated runtime configuration and explicit user processing approval are still required. Hosted and BYOK processing share provider-neutral application interfaces and preserve the user's chosen approved destination without fallback.

The checked-in production configuration enables Google login for the configured allowlist; missing secrets or invalid configuration keep it unavailable. To configure the implemented backend, an operator supplies `DB`, exact `AUTH_ENABLED=true`, and `AUTH_ORIGIN` (the approved HTTPS browser origin). Supply `AUTH_SECRET`, `AUTH_ALLOWED_EMAILS` (a JSON list of allowed verified email addresses), `AUTH_GOOGLE_CLIENT_ID` and `AUTH_GOOGLE_CLIENT_SECRET` through server secrets — set `AUTH_ALLOWED_EMAILS` with `pnpm --filter @invoxim/worker exec wrangler secret put AUTH_ALLOWED_EMAILS`, never as a Wrangler var. The registered Google redirect must exactly match `<AUTH_ORIGIN>/api/auth/callback/google`. No development relaxation of Secure cookies, origin checking or provider verification is implemented. Never commit secret values, reuse production resources in previews, or expose these bindings through Vite/public-config.

The login adapter requests only openid/email/profile. It discards provider access/refresh/ID tokens before account persistence and uses a domain-separated HKDF/AES-GCM key from server AUTH_SECRET to protect short-lived anonymous login state, bound to origin and hashed state identity. Rotating AUTH_SECRET invalidates sessions and pending login state; users restart login. The library owns cookies, PKCE, nonce and one-use state lifecycle. A narrow extension enforces signed Google identity claims with its public verifier. Real Google smoke testing still requires operator credentials and approved test identities. Public landing/demo login capability stays false until a reviewed operator-ready UI integration.

`createCredentialCipher` takes a validated server keyring `{activeVersion, keys}` where each key is a 32-byte base64url secret. Supply it from a platform/Wrangler secret at the future mailbox/inference composition boundary, never from a browser request, committed file or test key. Concrete adapter constructors take typed configuration, so tests can inject disposable synthetic values without embedding vendor choices in domain logic. Keyring encryption/rotation is implemented; wiring real provider callers remains their own tasks.

The credential vault is internal. Its read method supplies provider adapters in memory; metadata/settings projections contain only presence/revisions. It does not serialize external refresh calls: later mailbox adapters need a tested refresh lease before requesting a provider token. Local credential clear fences stale reads/writes; full disconnect, revocation and account deletion remain T15. No cloud resource, secret value, provider consent, deployment or production migration was created by this increment.

API responses apply no-store, nosniff, no-referrer and framing/CSP protections in the Worker. Static Pages headers are declared in web/public/\_headers; local Vite preview does not prove Cloudflare has applied them. Deployment/staging smoke tests must check the actual header policy and same-origin proxy before enabling real login. Current profile preference API reports valuations as not configured; FX rebuild is not falsely queued while T19 is absent.

## Durable jobs and Gmail consent

The production Wrangler configuration enables Gmail discovery, extraction and jobs with a 40-statement invocation budget. It binds the existing `invoxim-jobs` Queue as producer `JOBS` and consumer, with one message per batch, one concurrent consumer, three broker retries and `invoxim-jobs-dlq` for exhausted delivery. Application leases permit one tenant/global job at a time, three attempts and a five-minute lease/redelivery period. Secrets remain in Wrangler.

`JOBS_ENABLED=true` requires a configured D1 `DB` and Queue producer binding `JOBS`. Its configured minute Cron dispatches pending durable work and recovers expired delivery/leases; the stored `next_sync_at` policy still schedules recurring mailbox checks hourly. Both queues were confirmed to exist before binding them; no replacement queue was created. The Worker has one fetch/scheduled/queue composition root. Job records are durable in D1; delivery contains only `{schemaVersion: 1, jobId}`. Discovery and extraction handlers are composed only through their validated server flags/configuration; discovery readiness requires a current explicit review/start binding the account, range, selected processing configuration and hourly background authorization. Connections awaiting Start are excluded from scheduling.

Job policy variables are `JOBS_QUERY_LIMIT`, `JOBS_DISPATCH_LIMIT`, `JOBS_SCHEDULE_LIMIT`, `JOBS_TENANT_CONCURRENCY`, `JOBS_GLOBAL_CONCURRENCY`, `JOBS_MAX_ATTEMPTS`, `JOBS_LEASE_MS` and `JOBS_REDELIVERY_MS`. They use validated finite integer bounds. Missing bindings, disabled flags or invalid policy fail closed; they do not select another backend or allow unrestricted work.

Gmail consent uses `GMAIL_ENABLED=true`, a separately configured `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`, `CREDENTIAL_KEYRING` server-secret JSON and a validated `MAILBOX_LIMIT`. Its fixed callback is `<AUTH_ORIGIN>/api/oauth/mailbox/gmail/callback`. Google login and Gmail authorization credentials remain independent. The callback may validate provider identity and granted scopes, but cannot read messages or start an import. The callback redirects only to the fixed `/onboarding/review` path with a safe outcome code. That review UI is a deferred T29 integration seam; this increment does not claim a complete browser onboarding journey. Public capabilities remain disabled until operator readiness and UI integration are reviewed. Live consent testing and enabling cloud scheduling require separately recorded operator smoke evidence.

For scheduled/queue background entry points, the Worker creates one fresh invocation-scoped D1 execution budget (default 40). Jobs, discovery, credential reads and mailbox refresh receive the same guarded database handle. Individual statement methods and every statement inside a batch count against that shared limit; preparation/binding do not. Over-budget batches fail before submitting any statement. Native sessions share the counter, while unsupported bulk `exec`/`dump` fail closed in this background path. Job-store stage reservations also preserve recovery, scheduling and delivery progress. The configured dispatch limit is a maximum, not a guaranteed batch size. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) currently permit 50 queries per invocation on Free and 1,000 on Paid; bounded queries do not prove Free-plan CPU viability or deployed total costs. The environment seam permits 24–40 statements; smaller internal test budgets are not supported deployment settings. It does not select or upgrade a paid plan.

Changing an existing live stream's query mode is explicitly rejected. Non-advancing pagination tokens fail without staging or cursor advancement under the existing bounded retry policy. A future transition UI must respect these limits rather than reporting a successful unsupported change.

Document extraction accepts transient structured MIME parts through a provider-neutral interface. The concrete local PDF adapter supports a conservative uncompressed text-layer subset; compressed, encrypted, image-only and unsupported documents require review. It does not fetch assets, invoke a hosted converter or retain original bytes. Parser selection at the later processing composition boundary must use validated server settings and explicit destination consent. Provider-agnostic AI inference handles normalized text separately; no live model or external processing destination is enabled here.

## Optional LangSmith adapter tracing

Tracing is disabled when no enabling variable is supplied. The checked-in Wrangler configuration explicitly enables metadata-only tracing for the `invoxim-ai` project and leaves content capture disabled. It uses the pinned LangSmith SDK directly. The OpenAI-compatible adapter uses LangChain Chat Completions with automatic callbacks blocked; no LangGraph workflow engine is added. It covers OpenAI-compatible extraction calls and synthetic credential probes, for both hosted inference and BYOK. Clef classification and financial validation are outside this adapter trace.

Set these **Worker-only** Wrangler variables to enable metadata tracing:

```json
{
  "AI_TRACING_ENABLED": "true",
  "AI_TRACING_INCLUDE_CONTENT": "false",
  "LANGSMITH_PROJECT": "invoxim-ai",
  "LANGSMITH_HOST": "https://api.smith.langchain.com"
}
```

Store the credential interactively, never in JSON or frontend configuration:

```sh
pnpm --filter @invoxim/worker exec wrangler secret put LANGSMITH_API_KEY
```

Set `LANGSMITH_HOST` to the approved LangSmith HTTPS API origin (default `https://api.smith.langchain.com`; for example `https://eu.api.smith.langchain.com` for EU). A trailing slash is accepted; credentials, paths, query strings, fragments and control characters are rejected. Exports go only to that origin’s `/runs` endpoint; redirects are blocked and there is no fallback host. This is an operator-controlled Worker variable, never a client-supplied destination. The application maps `LANGSMITH_HOST` to the SDK’s explicit `apiUrl`; ambient `LANGSMITH_ENDPOINT` does not select a destination. Use a key authorized for the selected project; organization-scoped keys requiring an additional workspace selector are not supported by this initial configuration. `LANGSMITH_PROJECT` allows 1–80 ASCII letters, digits, dots, underscores and hyphens, beginning with a letter/digit. Exact `true` enables tracing; invalid optional tracing configuration disables only telemetry, leaving inference available. Set `AI_TRACING_ENABLED=false` to stop new exports.

Import traces contain only provider/model identifiers, prompt/schema versions, hosted/BYOK mode, elapsed time, generic status/reason, completion state and available usage counters. Missing usage is recorded as unavailable. No user/session/consent/source/attempt identifiers, email headers, receipt values, prompts, model output, provider credentials or exception text are exported. Each completed call gets an unrelated random trace ID. Metadata is allowlisted and runtime/environment enrichment is disabled.

`AI_TRACING_INCLUDE_CONTENT=true` permits bounded, credential-scrubbed input/output **only for the built-in synthetic credential probe**. Private imports remain metadata-only even when this flag is true. Sending private email/model content to LangSmith requires a separate processor-disclosure/consent implementation; this flag cannot override that boundary. Synthetic trace content is limited to 16,000 characters per input part and output.

A completed trace is sent immediately and awaited with a one-second deadline; there is no background batch requiring a later flush, no telemetry retry and no extra model request. Export failures emit only `ai_tracing_export_failed` and preserve the original inference result or exception. This can add up to one second to an enabled adapter call, including during a telemetry outage. No LangSmith key, production tracing enablement, deployment or live content upload is performed by adding this integration.

Verified API references: [custom instrumentation](https://docs.langchain.com/langsmith/annotate-code), [input/output privacy controls](https://docs.langchain.com/langsmith/mask-inputs-outputs), [serverless delivery](https://docs.langchain.com/langsmith/serverless-environments). Context7 was unavailable; SDK options were additionally checked against pinned `langsmith@0.10.11` types/source.

### Bounded import throughput

Production uses at most two concurrent Queue consumer invocations and two live
jobs globally/per workspace (`max_concurrency`, `JOBS_GLOBAL_CONCURRENCY`, and
`JOBS_TENANT_CONCURRENCY` are all 2). Keep `max_batch_size: 1`: each invocation
shares one actual 40-statement D1 budget across claiming, processing and
settlement. Increasing Queue batch size does not create another query budget.
Legacy oversized deliveries acknowledge only the processed item; untouched items
retry immediately into fresh invocations. Processing failures retain the existing
30-second delivery retry and durable exponential backoff.

Gmail content fetches two through eight unique attachment handles in one
`multipart/mixed` request to the discovery-defined
`https://gmail.googleapis.com/batch` endpoint. Single attachments retain the
ordinary GET. Relative paths and correlation IDs are generated by the adapter.
The entire source remains limited to 4 MiB decoded content, 64 MIME parts and
8 levels; metadata plus batch response share the existing encoded byte, chunk and
10-second request deadline bounds. Every inner response must match exactly once.
Any failed/malformed part discards partial transient results before either model
runs. No raw message content is persisted between stages.

Retryable Gmail failures retain the strictest valid outer/inner `Retry-After`
(seconds or standard HTTP-date) in the fenced durable job schedule. Ordinary
exponential backoff is a minimum; early duplicate deliveries cannot bypass the
cooldown. Unsupported delays over 24 hours or unsafe numeric headers pause work
with the existing service-unavailable state for operator recovery, rather than
retrying earlier than requested. Authentication failures keep the reconnect path.
Batching does not reduce Gmail quota units or change AI allowances/spending caps.
