# Server configuration seams

External adapters are constructed from validated environment bindings at the Worker boundary. Keep provider SDKs and environment reads out of core. T11 inference components and control-plane routes are locally verified; no hosted AI provider is selected or enabled by the checked-in configuration. Hosted and BYOK processing share provider-neutral application interfaces and preserve the user's chosen approved destination without fallback.

Google login is disabled by default. To configure the implemented backend, an operator supplies `DB`, exact `AUTH_ENABLED=true`, `AUTH_ORIGIN` (the approved HTTPS browser origin), and `AUTH_ALLOWED_EMAILS` (a JSON list of allowed verified email addresses). Supply `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID` and `AUTH_GOOGLE_CLIENT_SECRET` through server secrets. The registered Google redirect must exactly match `<AUTH_ORIGIN>/api/auth/callback/google`. No development relaxation of Secure cookies, origin checking or provider verification is implemented. Never commit secret values, reuse production resources in previews, or expose these bindings through Vite/public-config.

The login adapter requests only openid/email/profile. It discards provider access/refresh/ID tokens before account persistence and uses a domain-separated HKDF/AES-GCM key from server AUTH_SECRET to protect short-lived anonymous login state, bound to origin and hashed state identity. Rotating AUTH_SECRET invalidates sessions and pending login state; users restart login. The library owns cookies, PKCE, nonce and one-use state lifecycle. A narrow extension enforces signed Google identity claims with its public verifier. Real Google smoke testing still requires operator credentials and approved test identities. Public landing/demo login capability stays false until a reviewed operator-ready UI integration.

`createCredentialCipher` takes a validated server keyring `{activeVersion, keys}` where each key is a 32-byte base64url secret. Supply it from a platform/Wrangler secret at the future mailbox/inference composition boundary, never from a browser request, committed file or test key. Concrete adapter constructors take typed configuration, so tests can inject disposable synthetic values without embedding vendor choices in domain logic. Keyring encryption/rotation is implemented; wiring real provider callers remains their own tasks.

The credential vault is internal. Its read method supplies provider adapters in memory; metadata/settings projections contain only presence/revisions. It does not serialize external refresh calls: later mailbox adapters need a tested refresh lease before requesting a provider token. Local credential clear fences stale reads/writes; full disconnect, revocation and account deletion remain T15. No cloud resource, secret value, provider consent, deployment or production migration was created by this increment.

API responses apply no-store, nosniff, no-referrer and framing/CSP protections in the Worker. Static Pages headers are declared in web/public/\_headers; local Vite preview does not prove Cloudflare has applied them. Deployment/staging smoke tests must check the actual header policy and same-origin proxy before enabling real login. Current profile preference API reports valuations as not configured; FX rebuild is not falsely queued while T19 is absent.

## Durable jobs and Gmail consent

Checked-in Wrangler variables explicitly disable auth, AI, Gmail and jobs, with a 40-statement job budget. Secrets and resource identifiers are operator inputs.

`JOBS_ENABLED=true` requires a configured D1 `DB` and Queue producer binding `JOBS`. A configured Worker must also declare its Queue consumer and approved Cron trigger; no cloud resource is provisioned by this repository increment. The Worker has one fetch/scheduled/queue composition root. Job records are durable in D1; delivery contains only `{schemaVersion: 1, jobId}`. Discovery and extraction handlers are composed only through their validated server flags/configuration; discovery readiness continues to refuse new imports until T29 integrates explicit review/start.

Job policy variables are `JOBS_QUERY_LIMIT`, `JOBS_DISPATCH_LIMIT`, `JOBS_SCHEDULE_LIMIT`, `JOBS_TENANT_CONCURRENCY`, `JOBS_GLOBAL_CONCURRENCY`, `JOBS_MAX_ATTEMPTS`, `JOBS_LEASE_MS` and `JOBS_REDELIVERY_MS`. They use validated finite integer bounds. Missing bindings, disabled flags or invalid policy fail closed; they do not select another backend or allow unrestricted work.

Gmail consent uses `GMAIL_ENABLED=true`, a separately configured `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`, `CREDENTIAL_KEYRING` server-secret JSON and a validated `MAILBOX_LIMIT`. Its fixed callback is `<AUTH_ORIGIN>/api/oauth/mailbox/gmail/callback`. Google login and Gmail authorization credentials remain independent. The callback may validate provider identity and granted scopes, but cannot read messages or start an import. The callback redirects only to the fixed `/onboarding/review` path with a safe outcome code. That review UI is a deferred T29 integration seam; this increment does not claim a complete browser onboarding journey. Public capabilities remain disabled until operator readiness and UI integration are reviewed. Live consent testing and enabling cloud scheduling require separately recorded operator smoke evidence.

For scheduled/queue background entry points, the Worker creates one fresh invocation-scoped D1 execution budget (default 40). Jobs, discovery, credential reads and mailbox refresh receive the same guarded database handle. Individual statement methods and every statement inside a batch count against that shared limit; preparation/binding do not. Over-budget batches fail before submitting any statement. Native sessions share the counter, while unsupported bulk `exec`/`dump` fail closed in this background path. Job-store stage reservations also preserve recovery, scheduling and delivery progress. The configured dispatch limit is a maximum, not a guaranteed batch size. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) currently permit 50 queries per invocation on Free and 1,000 on Paid; bounded queries do not prove Free-plan CPU viability or deployed total costs. The environment seam permits 24–40 statements; smaller internal test budgets are not supported deployment settings. It does not select or upgrade a paid plan.

## Internal discovery and document parsing

`GMAIL_DISCOVERY_ENABLED` is false in checked-in Wrangler configuration. The Worker only constructs its concrete Gmail discovery adapter when that flag is exactly `true` and existing Gmail/login/keyring configuration validates. Application discovery interfaces remain provider-neutral. The same guarded D1 handle supplies the credential factory, serialized mailbox refresh, discovery service and job store. There is no silent provider fallback. Operator configuration alone does not authorize an import: the current processing-readiness port refuses work until explicit review/start and processing policy are integrated. No public Start endpoint or complete onboarding/import journey is enabled by this increment.

Changing an existing live stream's query mode is explicitly rejected. Range changes during active pagination/recovery are also rejected before provider work; cursors and buffered references are preserved. Idle live processing uses the latest approved parent start, and completed recovery clears only its temporary bounds. Non-advancing pagination tokens fail without staging or cursor advancement under the existing bounded retry policy. A future transition UI must respect these limits rather than reporting a successful unsupported change.

Document extraction accepts transient structured MIME parts through a provider-neutral interface. The concrete local PDF adapter supports a conservative uncompressed text-layer subset; compressed, encrypted, image-only and unsupported documents require review. It does not fetch assets, invoke a hosted converter or retain original bytes. Parser selection at the later processing composition boundary must use validated server settings and explicit destination consent. Provider-agnostic AI inference handles normalized text separately; no live model or external processing destination is enabled here.

## AI configuration (T11)

The Worker imports `config/ai.abacus.production.json` directly as server-side defaults for provider selection, approved models/notices/pricing and budgets. The selected preset enables AI settings; jobs/discovery/extraction remain separately gated. The adapter configuration seam still accepts `AI_REGISTRY_JSON`, a bounded, validated list of approved destinations and model capabilities, when an explicit environment override is intentionally supplied. `AI_HOSTED_DESTINATION` and `AI_HOSTED_MODEL` select an existing registry entry; `AI_HOSTED_KEY` is a server secret. `CREDENTIAL_KEYRING` protects user keys. `AI_BUDGET_JSON` supplies validated daily/monthly document and usage-unit limits plus exact decimal-string global USD-micro limits; both hosted and BYOK processing consume resource allowances. These variables never belong in Vite/public config or browser-selected endpoint URLs. Missing or invalid configuration fails closed; a user choice cannot silently fall back to another provider.

The current concrete protocol adapter accepts text through an approved HTTPS Chat Completions endpoint with a configured output-limit field and optional JSON-format/idempotency capabilities. It sends no tools, follows no redirects and bounds response bytes/time. Compatibility does not imply PDF/image/OCR support, provider quality, acceptable terms or a free service. Operator approval must bind model capabilities, current exact pricing and policy notices before live use.

Settings, synthetic connection testing and atomic hosted/BYOK usage controls are implemented and independently verified with synthetic data. They do not establish a complete processing/start-import path. Keep AI disabled until T11 evidence, later processing consent integration and separately recorded live provider checks are complete. See the owner inputs and unexecuted rollout gates in the root manual/deployment checklists.

Treat destination/model `configVersion` and processor `policyVersion` as immutable operator revisions: change them when endpoints, capabilities, pricing or processing terms change. The selected configuration is hashed for run/probe identity; stored settings and processing consent must match the approved revision. A synthetic passed probe proves only its fixed fixture/protocol at that configuration, not real-document quality or a ready import.

Metering retains upper reservations for possibly billed failures and pauses on reported overruns. Exact reported usage/cost totals are stored as decimal text in usage events; bounded aggregate counters retain their prior reservation if the actual charge cannot fit. A sticky hosted-global pause survives tenant deletion and later UTC periods. BYOK overruns pause that tenant's processing without charging operator funding. Recovery/reset must follow the later reviewed T24 runbook; there is no automatic reset that treats uncertain charges as free. An explicit environment override `AI_ENABLED=false` remains the immediate operator kill switch and takes precedence over the file defaults.

## Extraction-to-ledger pipeline (T12)

`EXTRACTION_ENABLED` defaults to `false`. The Worker composes the Gmail content adapter and approved AI factory only when this flag is exactly `true` existing Gmail/AI configuration validates and `JOBS_QUERY_LIMIT=40`. Smaller supported job budgets leave this extraction handler unavailable. Inference continues through the user's approved hosted/BYOK destination. Missing configuration leaves the handler unavailable. Setting a flag is not explicit processing consent; leased work must match the active profile, connection generation, accepted background consent, settings revision and disclosure.

The local pipeline uses metadata-only parse/infer/reconcile continuation jobs, preserving the existing durable job engine and one actual invocation database counter. Each queue invocation consumes at most one delivered job; additional messages retry. Configure a reviewed deployed Queue consumer batch size of one to match this bounded execution model; this repository does not provision a consumer. Inference makes one paid attempt per document stage; malformed output requires review, while the standalone bounded inference engine still supports its separately verified two-attempt repair policy. Current prompt revision 2 includes nullable source-grounded payment/refund references in its fingerprint.

Document bytes and parsed text are transient. Parse inventories bounded metadata; subsequent inference refetches the selected part, and reconciliation reads only the quote-free cache. The content reader's attachment/request limits and the supported conservative PDF subset remain explicit constraints. Distinct payments/refunds require reliable event identities; weak merchant/amount/day similarities remain review suggestions. Importing evidence preserves existing gross totals and manual fields. Conflicting versions remain visible for financial review.

## Separate Drive authorization and local connection controls

`DRIVE_ENABLED=false` is the checked-in default. Drive OAuth start/callback require valid login configuration, D1 with the storage authorization and consent structures in the consolidated `0001_initial.sql` baseline, the credential keyring, server variable `DRIVE_CLIENT_ID`, and platform secret `DRIVE_CLIENT_SECRET`. Register the exact HTTPS callback `/api/oauth/storage/google-drive/callback`. The Drive identity may differ from login and mailbox identities; requested scopes are `openid email profile https://www.googleapis.com/auth/drive.file`. Grant completion stores encrypted storage credentials and leaves archive consent disabled. It does not read mail, upload files or schedule jobs.

Authenticated `GET /api/storage/settings` returns bounded connection metadata, stored consent and a session-bound `storage-settings` mutation token. Send it in `X-Workspace-Token` for Drive start, local disconnect and consent-disable commands. Mutations require the exact application origin and an actually recent database session. `DELETE /api/connections/storage/:id` and `POST /api/storage/settings/disable` remain local operations when the OAuth feature or credentials are disabled; they never revoke shared Google grants or delete user Drive files. `GET /api/connections` lists bounded mailbox/storage metadata without requiring their external adapters, including legacy mailbox-only databases without storage authorization tables (the former migration sequence is retained only as compatibility fixtures).

Archiving capability remains false and there is no archive-enable/upload API yet. Explicit consent persistence is locally tested, but guarded original acquisition, planned-ID persistence, upload/resumable workflow, backfill and user interface integration remain unfinished. A connected Drive account is not an archived original. Do not enable live OAuth until registration, separate consent and the operator smoke gates are recorded.

## Optional operational observations

`OPERATIONAL_METRICS_ENABLED` defaults disabled. Enabling observations requires an operator-configured `OPERATIONAL_METRICS` service binding and platform secret `OPERATIONAL_METRICS_SECRET` (16–1024 printable non-space ASCII characters). `OPERATIONAL_METRICS_DEADLINE_MS` defaults to 25 and accepts 1–250. Invalid or incomplete configuration remains disabled. No service is created automatically.

The Worker sends only validated schedule, queue and cleanup aggregates to the bound service at `/v1/events`, using a fixed internal request URL and bearer authentication. The sink must acknowledge with 204 and honor cancellation. Events have no user, job, document, mailbox or provider identifiers, receipt values, titles, URLs or raw errors. A fresh invocation observer limits attempts to three and payloads to 512 UTF-8 bytes. Durations are wall time, not CPU; query counts come from the existing shared execution meter. Unknown failed-operation counts are represented explicitly rather than inferred as zero.

Observation errors cannot change scheduling, acknowledgement, retry or cleanup decisions. The sink, retention, recipients, thresholds and incident ownership require operator review (M12); local synthetic tests do not prove deployed delivery or monitoring effectiveness.
