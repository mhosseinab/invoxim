# Login authentication boundary (T05)

`createLoginAuth(DB, configuration)` uses Better Auth 1.7.7 with its verified Drizzle/D1 schema. The mapping keeps INTEGER epoch-millisecond auth timestamps and Boolean storage; Worker composition shares a native query meter across auth and repositories. The HTTP composition creates a fresh auth instance for **each request**; never cache or share an instance across callback requests. The `handleLoginCallback` entry point is one-shot per instance, with request-local new-user tracking. The wrapped database adapter records newly inserted user IDs before queued library hooks, only while this callback is active. Its cleanup deletes only users newly created by that callback with neither an account nor a session, allowing a fresh-state retry after a failed account write. It never sweeps existing users or merges by email. Database outage during cleanup can still require operator reconciliation; it cannot authorize session access or recreate a deleting profile.

The default is disabled. `loginConfiguration` returns a configuration only when `AUTH_ENABLED` is exactly `true`, DB is bound, and a fixed HTTPS `AUTH_ORIGIN` (origin only, no credentials), secret (32–1024 characters), Google client ID/secret, and a JSON array of 1–100 `AUTH_ALLOWED_EMAILS` validate. `createLoginAuth` takes that already-validated configuration (one configured rule). Real deployment/client configuration and independent review are operator prerequisites. Never put secrets in public Vite variables.

Google login requests only `openid email profile`, uses online access, disables incremental granted scopes and client ID-token sign-in, and prompts account selection. Better Auth owns PKCE, state, provider callback routing and session cookies. State uses the `database` strategy: a D1 verification row with a hashed identifier and ten-minute expiry, deleted on consumption, plus the library's signed state cookie check (not skipped). The `protected-login-state` plugin (`state-adapter.ts`) encrypts that verification value with AES-GCM under a key derived by HKDF from the auth secret and origin. The `verified-google-identity` plugin (`google-verification.ts`) requires an ID-token nonce, forwards it on the authorization URL, and calls the library's public `verifyGoogleIdToken` with the configured audience and expected nonce before normal profile mapping; subject, verified email, name, future expiry and the matching nonce are required. This login path is separate from the mailbox/Drive Google client in `mailbox/google-oauth.ts`.

The allowed-email rule is the single `isAllowedEmail` check in `configuration.ts` (S8): a case-insensitive match against the configured list, applied to new and returning OAuth identities. All account linking is disabled.

No login provider access/refresh/ID token is retained. Account create/update hooks discard token material and scope/expiry fields before the database adapter writes it; account cookies are disabled. Session cookie caching is disabled so logout/expiry/deleting status are checked against D1. Session cookies are Secure, HttpOnly, SameSite=Lax, path `/` and host-scoped (no Domain). Request headers and body/query user IDs never establish authority. The sole internal TenantContext assertion occurs after signed-session verification and active-profile lookup.

`handleLoginRequest` serves fixed sign-in, Google callback, sign-out and get-session routes under `/api/auth`; the Worker adds `GET/PATCH /api/me`. `readAuthJson` reads request bodies through the shared `src/http.ts` reader (default 4096 bytes, at most 40960) and maps its failures to 415 `unsupported_media_type`, 413 `request_too_large` or 400 `invalid_request`. Sign-in accepts only `provider: "google"`, an optional `callbackURL` of exactly `/` and `disableRedirect`; caller-selected scopes, ID tokens, arbitrary callback URLs and provider parameters are rejected. Unknown library routes return 404. Provider error descriptions are removed from callback redirects and errors are replaced by generic codes. Auth/profile responses are no-store and expose no bearer token or provider credential. Unexpected database/provider errors are mapped to generic unavailable responses; the library logger is disabled.

Profiles are created on identity provisioning without mailbox connections, consent, import jobs, Drive or model calls. PATCH preferences uses an active-tenant predicate and expected version. Originals are not converted by a preference change; the profile projection reports `valuation.status = not_configured`.

Synthetic workerd tests use real D1/session/callback/library/WebCrypto paths with exact Google transport interception and generated RSA/JWK fixtures. These prove application behavior locally; they are not live Google or deployed OAuth evidence.
